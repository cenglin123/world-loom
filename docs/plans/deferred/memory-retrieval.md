# 记忆召回设计备忘：重要性 vs 相关性

> 一次设计讨论的存档结论。**当前未实现**——零章节阶段用不上，到触发阈值再建。
> 回答的问题：要不要给人物记忆/关系加"打分权重系统"，让写作 agent 量化判断重要性？

## 结论一句话

**不建"注意力层"，不给记忆打"重要性分"喂给 agent。要做的是 RAG 检索，且只用于"选哪些记忆进上下文"。**

## 为什么不是"打分/注意力层"

讨论起点是想加一个"简易注意力层"给记忆打分，召回时让写作 agent 据此量化判断重要性。三个层层递进的纠正：

1. **静态重要性分 = 硬编码先验，违反本项目的 Bitter Lesson 原则。** LLM 打的分不可标定、会漂移（同一事件这次 7 分下次 5 分），还要额外校验维护，给已经很重的治理面再加一层。
2. **注意力测的是"相关性"，不是"重要性"——两者正交。** 注意力算的是 `similarity(当前场景, 记忆)`：一条关键记忆（核心背叛）在一场茶馆闲谈里相关性很低，一条无关紧要的喝茶记忆反而相关性高。把相关性分数贴上"重要性"标签喂给 agent，会系统性地误导它。
3. **注意力机制根本不需要自己造——它已经在写作模型内部。** Transformer 的 self-attention 会对 prompt 里每段内容自动加权。把记忆塞进上下文包的那一刻，写作模型就会对它做注意力加权。

所以这件事拆成两半，归属不同：

| 环节 | 谁负责 |
|------|--------|
| **选哪些记忆**进上下文（相关性召回） | 要建的基础设施 = **RAG 检索** |
| **进来之后怎么加权使用**（整合、判轻重） | 写作 LLM 自带的 self-attention，免费，别重复造 |

**一句话边界：基础设施负责"选准选全"，到此为止；绝不在基础设施里给记忆打一个标量再喂给模型——那是用粗糙外部标量覆盖模型更细的内部注意力，是降级。**

## 正确做法：重要性与相关性两条正交轴

| 轴 | 回答的问题 | 机制 | 对 agent 的作用 |
|----|-----------|------|----------------|
| **重要性** | 这条记忆对人物/剧情重不重要？ | 结构化：L1 层 + `锚点` 布尔标记 + "未解决的问题"挂起 | **保证注入** |
| **相关性** | 这条记忆跟当前场景相不相关？ | embedding 检索（RAG） | **排序/筛选其余部分** |

召回 = 先无条件注入"重要性挂起集"，再用相关性排序填满剩余预算。**agent 永远看不到"重要性数字"，它看到的是一组选好的散文，自己像小说家一样判断轻重。**

注：当前设计里"重要性"已部分免费——`L1 元记忆`=永久置顶；L2 条目只要"未解决的问题"还 open，就一直被注入，问题闭合后自然老化退出。`锚点` 布尔标记是对这套结构的补充，不是新的打分体系。

## 实现注意（到时候）

- **"简易" = 现成 embedding 的余弦相似度，不是可训练的注意力头。** 后者需要"查询↔记忆相关性"标注数据，一部小说产不出，别走这条路。
- **分数不入 git。** 它是依赖模型版本的浮点数，会随模型变化。**召回时现算、绝不持久化**，否则就把刚清理掉的"数据层漂移"问题又请回来了。
- **引入新依赖**（embedding + 向量索引）到一个目前纯 stdlib + markdown + git 的仓库，是一次真实的架构升级——过阈值才值得。

## 触发阈值（什么时候建）

- **现在不建。** 零章节，召回用现状的"最近 3-5 条 L2 + 所有未解决问题"（纯近因）完全够，上 embedding 索引是过度设计（Occam）。
- **建的信号**：L2 情节记忆累计涨到 **~数百条**（约几卷之后），近因召回开始可证地漏掉"相关但久远"的记忆时。届时把"最近 3-5 条"的纯近因召回，升级为"重要性挂起集 + 相关性 top-k"。

## 补充：要不要建知识图谱（KG）？

后续讨论的延伸问题。结论：**部分适用，但不是本问题的主工具，且现在不建——有用的 80% 你已经有了。**

### 事实：项目已有一个 proto 知识图谱

现有结构当图看，节点和边都已存在，只是分片在 markdown+JSON 里、由专用脚本查询：

- `relationships.json` 四格模型 = 角色节点之间的带属性边。
- frontmatter 的 `faction` / `tags`（所属/能力/等级/擅用）/ `world_position` = 角色到组织/能力/等级节点的类型化边。
- 章节 frontmatter 的 `characters_present` + `location` + `in_world_date` = 事件节点，连起角色×地点×时间。
- `check_chapters.py` 已在跑图约束查询（死角色不出场、同时不两地）= 图上的一致性检查。

所以问题不是"要不要有 KG"，而是"要不要把这套已存在的图**正式化**成图数据库"。

### 正式 KG 相对 RAG 多给什么

**结构化（关系型）召回**，与 RAG 的语义召回互补：RAG 给 `similarity(场景, 记忆)`（文本相近），KG 给图遍历（"本场角色 A 在地点 L → 拉出 A 的边、谁也在 L、哪些未闭合伏笔牵涉 A 或 L"）。KG 能捞到 RAG 漏的"相关但文字不相似"的事实。这是真价值。

### 但它不是本问题的主工具——三个理由

1. **只补最小的一块。** 重要性=结构标志（KG 帮不上），语义相关性=RAG，KG 只补"结构相关性"这第三、最小的一块，撑不起图数据库 + 抽取管线的成本。
2. **与项目哲学顶着干。** 项目押在 prose + LLM 语义判断（Bitter Lesson：谨慎手工写规则枚举）。用 KG 就得从散文抽取结构化三元组，而四格模型正因为是散文才有力——"A 表面信任 B、私下疑 B 毒杀师父、B 不知 A 已知"压成图的边，要么丢失要么逼出复杂到等于"用边重新发明散文"的 schema。
3. **第二个事实源 = 新漂移面。** 一个必须跟正文同步的完整 KG 把已有的同步压力成倍放大；用 LLM 自动抽取又把"别入 git"的非确定性请回来。

### 推荐：按需给已有的边加一层薄遍历，别建正式 KG

数据已在那（frontmatter + relationships.json）。真感到"关系型召回"痛时，写一个薄查询层（"给定角色 X + 地点 L，遍历出关联角色/伏笔/事件"）即可拿到 KG 召回 80% 的价值，不需图数据库、不需抽取管线、不引入第二事实源。散文仍是底料，脚本只遍历本就存在的边。真正该上图数据库：阵容/线头多到临时遍历脚本维护不动、且有消费方需要多跳查询时——大得多的小说的后期问题。

### 三轴合一（完整图景）

| 轴 | 机制 | 角色 | 何时上 |
|----|------|------|--------|
| 重要性 | 结构（L1/锚点/未解决问题） | 保证注入 | 现在就有 |
| 语义相关性 | RAG embedding | 填满预算 | L2 ~数百条 |
| 结构相关性 | 遍历已有的边（轻量）→ 极后期才上图库 | 补 RAG 漏的关联事实 | 阵容/线头爆炸时 |

三者互补不互斥。KG 是第三、最小、最晚才需要的那根轴。
