## 1. 两篇论文的落点

### 1.1 8 篇论文综合报告——"记忆流 + 反思 + 计划"是可运行模板

**Generative Agents（2023.04）** 是最接近角色扮演的已验证系统（25 Agent 小镇）。其架构三件套可直接映射到角色代理：

| Generative Agents | 角色代理对应 |
|---|---|
| **记忆流**（自然语言记录全部经历，时间戳 + 最近访问时间戳） | 角色 L2 记忆（场景/行动/判断/情感轨迹/未解决问题/对他人看法） |
| **反思**（定期合成高层 self-knowledge，附证据引用） | 角色在场景间歇的自我评估——"我刚才为什么那样做？" |
| **计划**（粗→细递归分解为 5-15 分钟动作） | 场景中角色的回合级决策——"基于三档目标，这一轮做什么？" |

**关键数据**：完整架构 vs 消融，TrueSkill 效应量 **d=8.16**——记忆+反思+计划的组合带来 8 个标准差的提升。这是架构级差异，不是小幅优化。

**但目标函数不同**：Generative Agents 追求**可信的人类行为**（believability），角色扮演追求**好看的戏剧**（drama）。SOTOPIA 基准里 GPT-4 在社交场景"过度礼貌/过度合作"（GOAL 4.85 vs 人类 5.95~6.15，p<0.05）的发现直接警告：**擅长"像人"的 Agent 可能在"出戏"上表现很差。**

### 1.2 12 系统评测报告——九个 Finding 中四个直接约束角色扮演

| Finding | 角色扮演的工程含义 |
|---|---|
| **F6·表示粒度**：保留可用证据 > 压缩 | 角色代理在场景中应看到**原始 L2 文本**而非摘要（LightMem Raw vs Summary 实证） |
| **F7·迟过滤原则**：写入时保留上下文，检索时再筛选 | 角色代理的上下文注入不应被 orchestrator 预先激进裁剪——给完整状态，让角色自己判断相关性 |
| **F9·保守合并** > 激进压缩 > 延迟刷新 | 场景结束后 L2 回写采用保守合并——宁可保留冗余，不丢"组合后才关键"的线索 |
| **F3·时序更新保真度**：可修订性内建于表示 | L2 过时需更新时（如"以为他背叛"→"发现是误会"），不删旧条目，**追加新条目并引用旧条目**（类 Zep 时间知识图谱），防"过去的幻觉"（hallucinations of the past） |

### 1.3 AMAC——记忆准入五因子约束 L2 回写

场景结束后**不是所有事情都值得写入 L2**。AMAC 的 Type Prior（内容类型先验）是贡献最大的单一因子（去掉后 F1 降 0.107）。对 L2 准入的直接含义：

| 应写入 L2 | 不应写入 L2 |
|---|---|
| 对他人看法的变化（关系改变） | 过渡性情绪波动（"有点烦"） |
| 关键决策及原因 | 感官细节（除非触发重要回忆） |
| 未解决的问题（新增或演化） | 场景中已被解决的问题 |
| 触及内核四维（欲望/恐惧/底线/应激）的事件 | 例行互动 |

## 2. 缺少的一层：运行态工作记忆

当前人物记忆是**文档态**（角色文件里的 L1/L2/L3 静态）。但角色代理需要**运行态**——场景进行中不断更新的工作记忆。这是 MemGPT 的核心洞察（主存=当前场景 / 外存=归档存储）：

```
┌── 角色代理运行时（主存 = 上下文窗口）────────────┐
│ 固定段  │ 角色内核（欲望/恐惧/底线/应激）+ 文风注册  │
│ 半固定  │ 本场 L2 注入集（recall.py 产出）        │
│ 动态段  │ 场景流：其他角色的发言/行动 → 我的反应     │
│         │ 内部独白：我观察到什么、我在想什么         │
│         │ 待决策：当前局势 vs 三档目标 → 行动选择   │
└──────────────────────────────────────────────┘
         ↕ 场景结束：保守合并（F9）→ L2 回写（AMAC 准入）
┌── 角色文件（外存）──────────────────────────┐
│ L1 元记忆（不变）                          │
│ L2 情节记忆（追加，主观视角，可修订引用）     │
│ 关系四格（可修订）                          │
└──────────────────────────────────────────────┘
```

**当前缺失的正是中间运行态层**——角色在场景进行中的实时状态。它在场景结束后大部分丢弃（= L3 瞬时记忆），少数按 AMAC 准入保守合并入 L2。

## 3. 边界厘清

### 3.1 角色扮演能解决、且"直接写"难以解决的

1. **真实博弈张力**：两角色目标不可调和（如沈照影要保护某人 vs 顾寒枝要清除威胁）——直接写时 agent 知道双方底牌，难写"一方真不知道另一方在想什么"的质感。独立代理各只知自己人设与目标，对抗更接近真实博弈。
2. **角色声音独立性**：不同文风注册（武侠/西域/宫廷/市井）在直接写中同处一个 agent"脑袋"里易趋同；独立代理各按自己的注册说话，自然分化。
3. **涌现性决策**：角色基于三档目标做选择，可能产生作者未预设的"意外合理"走向——Generative Agents 的核心发现（信息传播、社交协调皆涌现，非预设）。

### 3.2 角色扮演不能解决、且可能更差的

1. **文笔质量**：角色代理目标是"做出可信决策"，非"写出优美文字"。多代理各说各话 → orchestrator 收口拼合 → 最终文学质量**可能低于**单 agent 直接写（后者对整体节奏文风有统一把控）。
2. **节奏控制**：多代理博弈天然拖——每回合等所有代理推理。回合上限不是优雅方案，是止损线；拖到上限的强制收口可能比直接写更生硬。
3. **过度礼貌/合作倾向**：SOTOPIA 证据——LLM 的 helpfulness 训练使其竞争场景天然让步，两代理博弈可能出现"双方都主动退让"的反戏剧结果。
4. **成本**：参考 AgentSociety（10000 Agent 每轮 ~54K 次调用、~459 秒）。即使缩到 3-5 个角色代理 × 可能多轮，一个场景成本轻松超"直接写"5-10 倍。

### 3.3 判据：双向门槛

方法论 §4.3 的正向判据正确——**有效博弈方 ≥ 2 且目标冲突**。本计划补充**反向判据**：

> 即使满足"≥2 博弈方 + 目标冲突"，若场景中任何一方**没有真实决策空间**（剧情已决定结果，角色只是在"演"），则**不应**启用角色扮演。角色扮演的价值在"角色的决策改变剧情走向"；若走向已定，角色代理只是昂贵的提线木偶。

## 4. 推进路线（三阶段，严格次序）

### 第一阶段（即刻可行）· 强化"直接写"的记忆基础设施

**前提：角色扮演之前，先确保 L1/L2/L3 记忆系统实际运转。** 这本身就能显著提升"直接写"的质量。

- [ ] **验证 recall.py 的召回质量**：在 `writing` 分支写完 3-5 场后，人工检查 recall.py 的 L2 注入是否真覆盖"角色此刻应记得的事"。两篇论文一致强调：检索质量是记忆系统的基础。
- [ ] **建立 L2 准入纪律**：不是所有场景经历都写入 L2。按 AMAC 五因子的优先级——触及内核四维的事件 > 关系变化 > 新未解决问题 > 重要决策 > 日常互动。先由复盘 converge 中的 reviewer 软约束执行（系统已有 L2 更新检查），模式稳定后再考虑脚本化（**勿过早硬编码**，遵循 Bitter Lesson）。
- [ ] **建立 L2 可修订纪律**（F3）：L2 条目过时不删除，追加新条目引用旧条目，标注触发事件 + 时间点（已对齐方法论 §3.1 的"人设受控演化"留痕要求，扩展到记忆层）。

**退出条件**：直接写跑通 ≥1 卷，recall.py 召回质量经人工抽查确认，L2 无明显漂移。

### 第二阶段（实验验证）· 最小可行角色扮演 A/B 对照

**前提：第一阶段退出条件满足后才启动。**

选**一个满足双向判据**的场景（≥2 博弈方 + 目标冲突 + 双方有真实决策空间），做盲审对照：

- [ ] **A 组**：用"直接写"生成（当前默认）
- [ ] **B 组**：用角色扮演生成（每角色独立代理 + orchestrator 收口）
- [ ] **对照条件**：相同上下文包、相同人物卡、相同达成断言
- [ ] **评判**：独立 reviewer **盲审**（不知哪组是哪种方式），按 `docs/audit-checklist.md` 评分；建议 ≥2 个 reviewer 取共识

**可证伪心态（关键）**：若 B 组不优于 A 组（甚至更差），角色扮演应**继续搁置**，等待更强底层模型。方法论 §7.1：converge 审不出模型认知之外的东西；角色扮演同理——若底层模型在多代理博弈中表现不佳（SOTOPIA 证据指向此），增加架构复杂度不会改善，只会更贵。

**退出条件**：B 组在该场景类型上盲审显著优于 A 组 → 进入第三阶段；否则归档本计划，标注"当前模型下不推进"。

### 第三阶段（如验证通过）· 结构化实现

**前提：第二阶段对照证明角色扮演在特定场景类型上有优势。**

- [ ] **角色代理运行时**：轻量 Python 脚本，输入角色卡 + 场景状态 → 输出角色行动。核心是 prompt engineering（把人物卡四维变成角色代理的"思考框架"），不是复杂架构。
- [ ] **GM/Orchestrator 结构化**：借鉴 Concordia 的 GM（环境状态管理、物理约束检查、行动裁决）。但 Concordia GM 本身也是 LLM agent = 额外成本；先用手写"场景初始状态 + 终止条件"即可。
- [ ] **场景状态追踪**：场景中维护结构化"谁在哪、谁知道什么、什么变了"的共享状态对象，供所有角色代理读取——比每代理各维护独立世界模型更一致、更省 token。
- [ ] **L2 保守合并脚本**：场景结束时从运行态提取候选 L2，由 orchestrator 按 AMAC Type Prior 决策准入，写入保留主观视角 + 引用证据（F6/F9）。

**所有第三阶段项都在 A/B 对照通过后才有意义。**

## 6. 一句话总结

**角色扮演的瓶颈在记忆管理，不在对话生成。** 当前 L1/L2/L3 + recall.py + 写后回写已是正确结构骨架——在投入昂贵的多代理博弈前，先把这套记忆基础设施在"直接写"中跑通、验证召回质量与一致性。角色扮演的**边界**由"角色是否有真实决策空间"划定，**价值**由 A/B 对照盲审证明，**架构**由 Concordia 的 GM + MemGPT 的分层内存思路指导——但这些都在"先让直接写不出漂移"之后。
