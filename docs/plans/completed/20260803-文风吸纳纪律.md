# 文风吸纳纪律

> **这是使用层（分发仓）的制度**，落点在 `_分发/` 与源码层文档，不是开发层规范。
> 交接给接手 agent 执行；本文只定问题、边界与验收，不预写答案。

## 要解决的问题

用户要求"模仿某种文风来写"是这类项目的高频请求。分两种情况：

- **广为人知的作家**（金庸、古龙……）——模型训练时已经烂熟，不需要仓库做什么。
- **用户自己的文风，或用户想模仿的小众对象**——模型不知道。用户会甩过来几篇文章
  说"照这个写"。

第二种情况目前**在本仓完全没有制度承接**：样本放哪、总结出的规格算不算数、
算数的话谁授权、后面正文跑偏了谁发现——全是空的。结果就是文风只活在那一次对话里，
换个会话就漂了。

## 纪律的定位（最重要的一条）

**纪律不教 agent 怎么总结文风。**

不要写"文风特征清单"（句长分布 / 比喻密度 / 对话占比 / 意象偏好……）让 agent 填表。
那是把先验硬编进制度——遇到清单没覆盖的文风（比如靠标点节奏、靠信息克制、
靠视角距离来定调的）就会漏，而模型本来就有能力读几篇文章总结出调性。

纪律只管**四件事**：

1. **告诉 agent 有这回事**——用户给样本要求模仿时，这是一条有章可循的流程，
   不是即兴发挥。
2. **样本放哪**——可留存、可复核、可在换会话后重新对照。
3. **总结出的规格落到哪个权威源**——防止同一件事在两处各说各话。
4. **改动怎么授权、谁复核**——文风属锁定层，漂移即 bug。

一句话：**管存放、授权、复核，不管怎么总结。**

## 已知的制度约束（接手 agent 必须吃透）

| 约束 | 含义 |
|------|------|
| `docs/style-locked.md` 是文风的唯一权威源 | 锁定层（视角/时态/文风）。规格必须落在这里，不能另起炉灶 |
| 它在 `.githooks/commit-msg` 的 `GOVERNANCE_FILES` 里 | 改它的 commit 必须带 `[governance]` |
| 锁定层一旦锁定，漂移即 bug | 所以"换模仿对象"是一次**改锁**，不是随手改 |
| 用户样本是**内容层** | 绝不能进分发树。`scripts/layers.py` 是划分的唯一权威源 |
| `docs/writing-style.md` 是工艺层 | 技法与法则，和"这本书长什么样"分开，别混写 |

第三条尤其关键：分发仓是给下游用户的**空工具包**，任何一份用户样本泄漏出去
都是事故。加 pattern 后必须用 `python scripts/publish.py`（dry-run）复核清单。

## 需要接手 agent 做的决定

以下是真正的设计选择，本文不预设答案，但要求给出理由：

1. **样本存放位置**。候选：新建 `_文风/样本/`（与 `_方法/` 平行，语义清晰但多一个顶层目录）
   vs 复用 `docs/`（不增目录但语义混杂）。判据是 Occam 与可发现性。
2. **规格与样本的关系**。规格进 `style-locked.md`；样本是否需要长期保留？
   保留则可复核、可重新总结；不保留则更干净但无法追溯。
   注意与「素材是过路的」（`_方法/README.md` 的吸纳制度）对照——
   **两者结论未必相同**，因为文风规格需要长期比对，方法卡不需要。想清楚差别再定。
3. **多文风怎么办**。用户可能要求"主线用 A 的调子、回忆段用 B 的"。
   是允许 `style-locked.md` 记多套并标明适用范围，还是只允许一套？
4. **复核落点**。写完的正文跑没跑偏，靠 `05_复盘/reviewer-protocol.md` 的独立
   reviewer，还是靠卷末 converge？是否需要在 `docs/audit-checklist.md` 加一个维度？

## 机制化边界

拿 [[docs/development]]「机制化三分判据」逐条过一遍再决定写不写脚本。初步判断：

**可以机制化**（契约层，fail-closed）：
- 样本目录非空但 `style-locked.md` 文风段仍是待填写 → 说明吸纳没走完
- 样本路径的层归属（内容层，不分发）→ 加进 `layers.py` 的 `CONTENT_PATTERNS`

**不要机制化**（判断层）：
- 文风总结得对不对
- 正文像不像那个调子

第二类交给 reviewer 与 converge。**任何试图用脚本给文风打分的设计都要拒绝**——
那正是苦涩的教训反复证明会失败的做法。

## 落点清单

| 文件 | 改什么 |

| `_分发/AGENTS.md` | 加一条指针，让 agent 知道有这条流程。**注意词数预算**（现 362/400） |

## 验收

```bash
python scripts/check_all.py --quiet
python scripts/publish.py              # dry-run，确认样本路径不在清单里
```

外加一次人工复核：**假装自己是下游用户，从分发树全新 clone 走一遍**——
"我有三篇文章，想让你照这个风格写"，看 agent 能不能只凭仓库里的文档走完全程。
走不通说明纪律没写清楚，或者根本没让 agent 知道它存在。

## 执行记录（2026-08-03）

四个决定的结论与理由：

1. **样本存放** → `06_文风样本/`。编号 = 内容层（用户产物）、下划线 = 源码层（随仓工具）——
   样本是用户内容，前缀语义必须一致；`_模板/` 镜像也随之回归正常形态。
2. **样本长期保留**。与方法素材"过路"的差别：方法卡吸纳后是自足的操作指令，丢了对执行无损；
   文风规格是有损压缩，复核"跑没跑偏"、换锁前比对、重新总结都要回到原文。
3. **允许多套并存**，每条目靠「适用范围」划界，单套不填 = 全书默认。与注册表的多注册 + 主/副设计同构。
4. **复核双落点**：reviewer 审理素材第 8 项注入样本（软阻断判定基线）+ audit-checklist 加调性一致性项。
   卷末 converge 本就走 reviewer 协议，不另加机制。

机制化只落一处契约检查（check_docs.py：样本已入库但「文风模仿」段无 `###` 条目 → FAIL），
总结质量与调性判断全部留给 reviewer。

测试材料仅用于验证，已弃置不入库。
